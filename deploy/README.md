# Deployment examples

Build the server and console together with `npm ci && npm run build`. Run one service process; it starts the model proxy and, when enabled in V2 config, the separate admin listener. Keep the config, control database, usage database, encrypted secrets, and backups in one persistent `dataDir`. Do not copy only a SQLite main file while WAL is active; use the console's coordinated backup operation.

## Docker Compose

From the repository root, run `docker compose -f deploy/docker/compose.yaml up --build -d`. The image pins Node 22.16.0. On the first start the entrypoint copies a valid empty V2 config to `/data/config.json`; subsequent starts preserve that file and all other state in the `model-router-data` volume. The service runs as the image's unprivileged `node` user. If replacing the named volume with a host bind mount, make its directory writable by that user.

The Compose file publishes the proxy on host `127.0.0.1:15005` and the admin UI/API on host `127.0.0.1:15006` as separate mappings. The container binds `0.0.0.0` internally so those mappings work. The bootstrap token appears in `docker compose -f deploy/docker/compose.yaml logs model-router` on first launch and expires after 15 minutes. The backend requires a loopback peer for bootstrap; Docker's published port is **not** a loopback peer inside the container. Create the administrator from inside the container with `docker compose -f deploy/docker/compose.yaml exec -it model-router node /opt/model-router/bootstrap.mjs`, then open `http://127.0.0.1:15006/admin/` locally and sign in. The helper prompts for the token and password without echoing them. Never publish the admin port directly to an untrusted network.

Before remote access, edit the persisted V2 config and set a unique `instanceId`, `server.publicProxyBaseUrl` (for example `https://api.example.com`), and `admin.publicAdminBaseUrl` (for example `https://admin.example.com`). Restart after listener/public admin URL changes. The admin URL must exactly match the browser's Origin for authenticated writes. The example [nginx config](docker/nginx.conf.example) terminates TLS on separate hostnames and forwards to the two loopback ports. Replace hostnames and certificate paths. Its buffering settings keep both model streams and `/admin/api/v1/events` SSE responsive; preserve `proxy_http_version 1.1`, `proxy_buffering off`, a long `proxy_read_timeout`, and forward the original Host/Origin.

The starter config does not trust any `X-Forwarded-For` source. If client IP forwarding is required, identify the actual address/CIDR of your controlled reverse proxy as seen by the app and set `server.trustedProxyCidrs` to that narrow range. Do not enable blanket trust for arbitrary clients. The default public URLs are local HTTP values for initial setup only.

## systemd

[model-router.service](systemd/model-router.service) is a system service example. Install the built repository at `/opt/model-router`, create a `model-router` system account, and place its V2 config at `/var/lib/model-router/config.json` (or let the service generate the local default there on first start). `StateDirectory=model-router` supplies a persistent, service-owned data directory. Set `storage.dataDir` to `/var/lib/model-router` and choose the public URLs and bind addresses appropriate for your reverse proxy. Install the unit as `/etc/systemd/system/model-router.service`, then run `systemctl daemon-reload` and `systemctl enable --now model-router`. Use `journalctl -u model-router -f` for logs. Adjust `/usr/bin/node` if Node is installed elsewhere. The process stays in the foreground; do not add the CLI `--daemon` flag under systemd.

## launchd

[com.modelrouter.plist](launchd/com.modelrouter.plist) is a per-user LaunchAgent example. Install the built repository at `/usr/local/share/model-router`, replace `REPLACE_ME` with the account name, and adjust the Node path (Apple Silicon Homebrew commonly uses `/opt/homebrew/bin/node`). Place the plist in `~/Library/LaunchAgents/`, create the config directory under `~/Library/Application Support/model-router/`, then run `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.modelrouter.plist`. Use `launchctl bootout gui/$(id -u) ~/Library/LaunchAgents/com.modelrouter.plist` to stop it. Its config location is persistent across restarts; keep both listeners on loopback unless a local TLS reverse proxy serves them. The agent runs the CLI in the foreground.

## Managed SaaS startup contract

Managed SaaS is selected from the process environment; it does not use the local V2 JSON config or local SQLite state. The Docker Compose, systemd, and launchd examples above describe the local/self-hosted runtime. The Compose file does not configure SaaS databases, Redis, provider modules, or role-specific listeners. The contract is implemented in [deployment.ts](../src/saas/deployment.ts) and [managed-saas.ts](../src/server/managed-saas.ts).

Managed SaaS requires PostgreSQL 15 or later. The role template and the production startup probe both reject older server versions. Use a currently supported minor release and keep it patched.

Build the release, apply the database migrations explicitly, create the first platform administrator, then start the service in the foreground. Supply database credentials and other secrets through the process supervisor or a secret manager; do not put them in source control or command-line arguments. The two one-shot management commands read `MODEL_ROUTER_SAAS_DATABASE_URL` (the generic migration/management connection), while a role-specific service uses its role-specific database variable.

```sh
npm ci
npm run build
node dist/cli/index.js saas:migrate
node dist/cli/index.js saas:bootstrap-admin
node dist/cli/index.js start
```

Run the bootstrap command from a secure interactive TTY; it prompts for the first platform administrator's details. Startup checks PostgreSQL connectivity and schema compatibility for every managed role. Control-plane workloads additionally verify the effective database role and configured providers before binding listeners; the credential-validation worker uses its own column-scoped PostgreSQL privilege probe and decrypt-only KMS adapter and opens no listener. Startup never applies migrations automatically, falls back to local mode, or creates local SQLite state for a managed SaaS deployment.

In production, startup checks the effective PostgreSQL session before loading providers or opening listeners. The connection must remain the direct login role, have no role memberships or object ownership, and use exactly `model_router_saas` as its explicit `search_path` (with PostgreSQL implicitly searching `pg_catalog` first). It allows only `SELECT`/`INSERT`/`UPDATE` table DML (with `DELETE` permitted solely on `saas_billing_spending_freezes`), sequence `USAGE`, and ordinary in-schema function execution. The probe rejects column-level access outside that contract, PG 17+ `MAINTAIN`, `SECURITY DEFINER` routines, and any executable/access-granted application object outside schemas the role can use. Database/schema creation, temporary objects, `TRUNCATE`, and other extra privileges fail startup. Apply the dedicated-database role template below and verify the runtime URL authenticates as `model_router_saas_control_plane`; splitting URLs without distinct restricted PostgreSQL roles is not sufficient.

For a live, read-only probe, configure a disposable database with the role template and completed migrations, rerun the template to reconcile grants, then set `MODEL_ROUTER_SAAS_RUNTIME_PRIVILEGE_TEST_URL` to that control-plane URL and run `node --import tsx --test tests/saas/db/runtime-privileges.integration.test.ts`. The test only runs `SELECT current_user` and the privilege probe; it is skipped when the variable is absent.

Every managed SaaS process requires `MODEL_ROUTER_DEPLOYMENT_MODE=managed-saas` and a role-specific PostgreSQL URL. The customer/platform `combined` and `control-plane` roles additionally require `MODEL_ROUTER_SAAS_REDIS_URL` (`redis://` or `rediss://`), `MODEL_ROUTER_SAAS_REDIS_PROVIDER`, and `MODEL_ROUTER_SAAS_KMS_PROVIDER`. Those module settings are trusted Node module specifiers, not provider names or cloud credentials: Redis exports `createRedisProvider`; the credential module exports `createCredentialKeyProvider` for the platform TOTP credential-key contract. This credential-key provider is separate from `SAAS_PROVIDER_CREDENTIAL_SEAL_KMS_MODULE`, which seals platform provider credentials. Modules are executable code loaded into the service process, so install and reference only modules you control. KMS factories receive a copied snapshot of the process environment; keep unrelated secrets out of each workload.

The gateway has a separate provider contract. It requires `MODEL_ROUTER_SAAS_GATEWAY_DATABASE_URL`, the gateway listener, `SAAS_GATEWAY_PROVIDER_CREDENTIAL_DECRYPT_KMS_MODULE`, and stable `MODEL_ROUTER_SAAS_DEPLOYMENT_ID` and `MODEL_ROUTER_SAAS_ENVIRONMENT_ID` context IDs. It must receive only its gateway database URL and listener declarations: the parser rejects the generic management, control-plane, and worker database variables plus customer/platform listeners. It does not require Redis, the platform TOTP credential-key provider, or provider-sealing settings, and rejects those control-plane declarations if they are present. The gateway module must export `createGatewayProviderCredentialUnsealingKms({ env })` with `decryptDataKey`, `checkReady`, and `close`; give its workload identity only the permissions needed to decrypt provider-credential data keys and check readiness, never to generate or wrap them. Gateway scheduler and capacity dependencies are injected through gateway ports; the current gateway scheduler has no Redis setting/client dependency, and capacity reservations receive the PostgreSQL executor. There is no Redis requirement evidenced by the current gateway implementation.

The gateway also requires `MODEL_ROUTER_SAAS_GATEWAY_RUNTIME_MODULE`. The runtime module exports `createManagedSaasGatewayRuntime({ database, deployment, env, lifecycle })` and returns exactly `dependencies`, `checkReady()`, and `close()`. It supplies project-entitlement resolution, scheduler health and affinity authorities, the provider-lease concurrency limit, route and provider capability configuration, evidence signing and verifier keys, upstream route resolution, and authentication-header resolution. The module's readiness check must confirm its declared lease limit matches its `PostgresProviderAccountLeaseService`; core also rejects a mismatch against the configured gateway `maxConcurrency`. The health authority must use durable authoritative health state—there is no in-memory healthy default—and affinity must resolve only durable server-validated references. The module cannot provide an HTTP handler or bind a listener. Core validates the contract, constructs the PostgreSQL scheduler and production composition, owns the `/v1` listener, and wires the existing PostgreSQL caller/admission/attempt/compensation/entitlement and capacity adapters. Capacity admission fails closed unless all tenant, project, and key request-rate, token-rate, and concurrency limits are present and valid.

The runtime module is trusted executable code, not a turnkey production adapter. Production health-port integration with migration 040 still requires migration registration and runtime-module wiring, and the repository has no durable affinity mapping yet (affinity-dependent requests must block until one is supplied). Production project-entitlement resolution, route resolution, provider usage estimation/model compatibility, evidence signing and verifier-key provisioning, and upstream authentication-header resolution also remain runtime-module responsibilities. Supply and independently verify those adapters before treating gateway traffic as production-ready. Module load or listener bind does not constitute commercial or end-to-end acceptance.

### Workload roles and listeners

`MODEL_ROUTER_SAAS_WORKLOAD_ROLE` accepts exactly the roles below. In production (`NODE_ENV=production`) it is required and `combined` is rejected. The selected role must use its matching PostgreSQL variable; there is no fallback from a role-specific URL to `MODEL_ROUTER_SAAS_DATABASE_URL`.

| Role | PostgreSQL variable | Listeners selected by the contract | Current standard CLI status |
| --- | --- | --- | --- |
| `combined` | `MODEL_ROUTER_SAAS_DATABASE_URL` | customer `/console`, platform `/admin`, gateway `/v1` | Development/test only; not accepted in production. Without the compatibility gateway composition, `/v1` returns `503 GATEWAY_UNAVAILABLE`. |
| `control-plane` | `MODEL_ROUTER_SAAS_CONTROL_PLANE_DATABASE_URL` | customer `/console`, platform `/admin` | Supported by `model-router start`; no inference listener is opened. |
| `gateway` | `MODEL_ROUTER_SAAS_GATEWAY_DATABASE_URL` | gateway `/v1` | Standard CLI composition loads the trusted runtime module. Startup fails closed if its dependencies, readiness, or decrypt-only KMS are unavailable. |
| `credential-validation-worker` | `MODEL_ROUTER_SAAS_VALIDATION_WORKER_DATABASE_URL` | none | Supported by `model-router start`; runs only the durable credential-validation loop with its dedicated decrypt-only KMS adapter. |

For every selected listener, set all three corresponding variables: `MODEL_ROUTER_SAAS_<CUSTOMER|PLATFORM|GATEWAY>_BIND_ADDRESS`, `_PORT`, and `_ORIGIN`. Ports must be decimal TCP ports from 1 through 65535 and must not have leading zeroes. Bind addresses are the addresses the process actually listens on. Keep them private or on loopback behind a controlled ingress; a listener is plain HTTP, so terminate TLS at the ingress. `ORIGIN` is the exact public browser/API origin, with no path, query, fragment, or credentials. Non-loopback origins must use HTTPS; loopback HTTP origins are allowed for development. The handlers own the fixed prefixes `/console`, `/admin`, and `/v1`; preserve those prefixes through the ingress. Give each listener a non-overlapping socket binding: the parser rejects exact duplicate address/port pairs, but overlapping wildcard bindings can still fail when the OS binds them. The listeners may share a public origin if the ingress dispatches by those paths.

The production `control-plane` role requires the customer and platform listener variables above, plus `NODE_ENV=production` and stable `MODEL_ROUTER_SAAS_DEPLOYMENT_ID` and `MODEL_ROUTER_SAAS_ENVIRONMENT_ID`. The validation worker also requires these context IDs, but has no listener, Redis, TOTP credential-key provider, or provider-sealing KMS dependency. The IDs are non-secret context labels (1–128 characters; begin with a letter or digit and then use only letters, digits, `.`, `_`, `:`, or `-`). Use distinct values for isolated deployments/environments and keep them unchanged while stored provider credentials may need to be unsealed.

The gateway requires stable deployment and environment context IDs whenever its decrypt-only KMS module is configured (the module is mandatory for this role, including outside production). Its module setting is independent from both the control-plane provider-sealing KMS module and the validation-worker decrypt-only module. Keep these settings and workload identities separate; the gateway must not receive the control-plane Redis, TOTP credential-key, provider-sealing module, or sealing key reference.

Production `control-plane` also requires both `SAAS_PROVIDER_CREDENTIAL_SEAL_KMS_MODULE` and `MODEL_ROUTER_SAAS_PROVIDER_CREDENTIAL_KMS_KEY_ID`; configure both or neither in non-production. The module must export `createProviderCredentialSealingKms({ env })` and return `generateDataKey`, `checkReady`, and `close` methods. The key ID is a non-secret KMS key reference, not key material. Give this adapter only the KMS permissions needed to generate/wrap data keys and perform its readiness check; it must not have data-key decrypt permission. Keep the deployment/environment IDs stable because they are part of the credential encryption context. If the pair is absent outside production, the platform supply credential service is not mounted; there is no plaintext fallback.

`MODEL_ROUTER_SAAS_DATABASE_URL` remains required by the one-shot `saas:migrate` and `saas:bootstrap-admin` commands, even when the production service uses `MODEL_ROUTER_SAAS_CONTROL_PLANE_DATABASE_URL`. Give `saas:migrate` a migration-capable URL, `saas:bootstrap-admin` an appropriately restricted management URL, and each long-running service its own least-privilege role URL. Run `deploy/managed-saas-postgres-roles.sql` before the first migration and again after migrations so the scoped freeze-release DELETE grant is applied. Reapply it after future migrations that add application objects; default ACLs provide ordinary control-plane DML/sequence/function rights, while startup fails closed until each role's privilege set is reconciled. The standard CLI supports the credential-validation worker and gateway runtime-module startup; gateway production readiness still depends on the missing adapters listed above.

For the validation worker, configure only `MODEL_ROUTER_SAAS_VALIDATION_WORKER_DATABASE_URL`, `SAAS_VALIDATION_WORKER_PROVIDER_CREDENTIAL_DECRYPT_KMS_MODULE`, and the stable deployment/environment context IDs. Do not place control-plane, gateway, listener, Redis, TOTP KMS, or provider-sealing settings in this workload. The trusted module must export exactly `createCredentialValidationWorkerUnsealingKms({ env })` and return only `decryptDataKey`, `checkReady`, and `close`; provision a separate workload identity limited to decrypting provider-credential data keys under the expected key and encryption-context conditions. Do not grant data-key generation/sealing permission. This KMS adapter and module setting are independent from the gateway KMS facade.

After migration 035 is applied and `deploy/managed-saas-postgres-roles.sql` has reconciled the schema, run `deploy/managed-saas-validation-worker-role-grants.sql` as a database administrator. It creates/reconciles the standalone `model_router_saas_validation_worker` role and grants only column-level reads for validation snapshots/envelopes and column-level updates for leases and credential health. It grants no table-level DML, inserts, deletes, sequence use, or routine execution. Set the worker database URL to this role; production startup rejects broader privileges, role memberships, object ownership, or an unsafe search path.

The worker stores no secret in its job. Credential creation and job enqueue are one transaction; jobs contain only tenant/account/credential-version identity, provider/product, approved model/endpoint snapshots, and idempotency metadata. Lease and completion decisions use database time and fencing generations; rotation, revocation, or disable cancels old work. The worker can update only credential/account validation health and lifecycle status—not provider rights, catalog capabilities, entitlements, plans, or wallet balances. It uses fixed server-owned HTTPS adapter targets with redirects disabled and a bounded timeout/response policy. The initial adapters cover only Kimi Platform (CN/global) and DeepSeek Chat `api-key` / `chat-completions`; Kimi Code, DeepSeek Anthropic, custom providers, arbitrary endpoints, and unverified protocols fail closed. This is not evidence that every provider protocol is compatible.

## CI and live tests

The workflow in `.github/workflows/ci.yml` pins Node 22.16.0 on Ubuntu 24.04 and runs `npm ci`, `npm run build`, `npm test`, and a separate Chromium-backed `npm run test:e2e`. The optional local Ollama live test is not part of CI; run `npm run test:live:ollama` separately on a machine with the intended model installed. Kimi and DeepSeek live smoke tests require explicit provider-specific credentials and model names. CI never requires local model access or cloud credentials.
