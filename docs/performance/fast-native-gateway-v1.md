# Native fast gateway, first vertical slice

Status: implemented behind an **off-by-default** flag; paid native integration and a clean automatic-default, actual-estimator sustained paired run have passed; finite-repeat latency variance and credit-admission failures remain under investigation. This is a separate data plane, not another small reduction in the legacy proof chain. No deployment is implied.

## Ordinary warm request

1. Existing HTTP authentication, request limits and moderation remain. Authoritative routing, entitlement, price and sealed credential policy are cached for an absolute maximum of 5 seconds. Cold loads retain their original validation timestamp; cache hits never extend it.
2. Deployment model compatibility and authentication-header policy callbacks are captured only on cold load. The built-in callbacks normally perform PostgreSQL queries; the fast compiler/transport use exact-bound frozen facts instead. Core authority uses one repeatable-read transaction; these auxiliary deployment callbacks are a separately observed bounded view, not falsely claimed to share that transaction.
3. One Redis Lua admission enforces operational rate/token/concurrency limits. Redis is not the money authority. Missing sentinel, lost connection and unsafe eviction policy fail closed; restart quarantine is explicit.
4. One PostgreSQL autocommit statement reserves a genuine maximum charge from prepaid instance credit and inserts the immutable may-send intent. No global wallet lock, prepared-evidence registration, preflight, claim or dispatch-proof reread occurs here. Duplicate/ambiguous acknowledgement never authorizes another send.
5. A private one-use ticket drives the existing HTTP transport, including endpoint/DNS/header protections and credential unsealing. Authority expiry is checked after intent acknowledgement and again at ticket/credential consumption.
6. Exact observed usage is validated against the same journal calculator before a durable receipt acknowledgement. JSON final byte/EOF and SSE terminal DONE/EOF wait for that acknowledgement; preceding SSE events stream normally. The durable billing worker posts an idempotent exact ledger effect asynchronously.

Target: **0 warm metadata PostgreSQL queries + 1 pre-upstream intent statement**. Cold loads, receipt persistence, asynchronous billing, refill, health polling and legacy fallbacks must be reported separately. Warm paid native HTTP has demonstrated this blocking-path budget; periodic background moderation refresh is still included in whole-window SQL and can inherit request diagnostic context. Initial acceptance goals are serial 15–20 ms and at least 300 RPS in the existing paired local mock conditions, then at least 90% of paired sub2api throughput, with financial drains and crash gates passing.

## Enable only in an isolated validation deployment

- `MODEL_ROUTER_FAST_GATEWAY=reserved-max`
- `MODEL_ROUTER_FAST_REDIS_URL` (or existing `MODEL_ROUTER_SAAS_GATEWAY_REDIS_URL`)
- `MODEL_ROUTER_FAST_NAMESPACE`: deployment-specific shared namespace
- `MODEL_ROUTER_FAST_OWNER`: stable unique gateway-instance allocation identity
- `MODEL_ROUTER_FAST_CREDIT_TRANCHE_MINOR_UNITS`: optional explicit positive hard cap; unset uses wallet-backed automatic liquidity sizing
- `MODEL_ROUTER_FAST_REDIS_DRAINED=1`: only for a proven fresh/drained Redis namespace; never blindly on restart
- Optional `MODEL_ROUTER_FAST_SNAPSHOT_KEY_BASE64`: deployment-owned 32-byte AES key enables encrypted shared Redis L2. Without it the bounded L1 cache is used. Never use an API/provider secret as this key.

The equivalent `fastGateway` production-composition option is available for isolated native fixtures. Migrations through 145 and their explicit restricted-role grants are required. The first cold credit preparation is bounded and coalesced before the intent; warmed requests do not add a credit-query round trip. Actual insufficient prepaid capacity rejects that request; it does not silently bill free or fall through after an intent. Keep the same instance owner exclusive across live replicas; owner epochs fence an older process.

Response headers identify selection: `x-model-router-execution-mode: fast-reserved-max` or `strict`, with `x-model-router-fast-fallback` for unsupported work. Benchmark acceptance must assert paid fast selection, not infer it from a flag.

## Initial supported and fallback scope

Supported: ordinary OpenAI-compatible `/v1/chat/completions`, text-only message strings, a positive output bound in the final compiled upstream payload, one choice, default service tier, API-key credentials, ordinary token pricing, platform prepaid or BYOK, JSON or SSE.

Before any fast intent, these use strict mode: client idempotency keys; other operations/protocols; tools/audio/images/non-text content; absent final compiled output ceiling; multiple choices; special service tiers; per-unit/token-multiplier or advanced group finance; finite key monetary/token budgets; OAuth or special account controls; bound egress proxy/TLS profiles. Native policy denial is not a fallback permission. Verified active accounts without PG health history are neutral schedulable; a historical probe timestamp does not invalidate a healthy/degraded account. Current cooldown and unhealthy/half-open states still exclude candidates. The current first slice selects the first eligible candidate; it does not claim general multi-account scheduling or safe post-send retries. Completed 429/5xx outcomes update bounded Redis cooldown; ambiguous remote execution retains its slot conservatively.

## Deliberately changed contracts

- Authority revocation/spending-freeze visibility is bounded by the original **5-second hard snapshot lease**, not immediate per-send PostgreSQL locking. No durable invalidation outbox is claimed yet. Local invalidation/outage hooks fail closed.
- Money stays conservative: a hard enforceable maximum, not an ML estimate; unknown usage retains its reserved liability indefinitely pending explicit reconciliation. Credit cannot be recycled by a timeout. Legacy wallet/refund/correction paths account for allocation backing.
- A completed response has a durable receipt before terminal completion. A crash after upstream send but before a receipt remains UNKNOWN; exact provider usage is not magically reconstructible without upstream lookup. No automatic replay, fake refund or silent deletion resolves that ambiguity.
- Redis operational lease horizons bound capacity recovery, not a proof that a remote provider stopped after cancellation. Production Redis must use `noeviction`; connection loss requires explicit managed recovery.
- Fast Redis operational counters are separate from legacy PG capacity and the optional legacy Redis quota store. Mixed fast/strict traffic has **per-plane**, not combined, RPM/TPM/concurrency bounds; with equal stable limits the aggregate can approach twice one plane's cap. Wallet backing and ledger conservation remain shared. Initial rollout must isolate the relevant tenant/key **and shared provider-account** quota scopes, or explicitly accept these summed operational bounds. Enabling fast mode alone is not isolation: unsupported requests still fall back to strict mode. Unified cross-plane operational admission is a separate follow-up, not a reason to restore per-request PG proof chains.
- Credential plaintext is never serialized to the snapshot or journal. This slice still unseals per request; local software-KMS benchmark results cannot promise remote-KMS latency.

Rollback disables the flag for **new requests**, while the durable receipt worker/recovery must continue draining existing fast intents. Never replay a may-send fast intent through strict mode. Schema/credit liabilities cannot be dropped until reconciled.

## Validation at the integration checkpoint

Focused tests cover paid JSON/SSE reserve and exact usage; mixed-case SSE media type; durable terminal barrier; duplicate and lost intent acknowledgement; expiry during intent wait; strict pre-intent fallback; receipt storage failure; cold-only callback invocation and exact routing identity; unsafe header rejection. Existing HTTP/composition regressions remain green. Real restricted-role PostgreSQL/Redis tests are separately supplied by the journal, snapshots and admission components. Native paid HTTP and request-scoped SQL census have passed; finite paired runs with an explicit adequately funded tranche reached 95–101% of contemporaneous sub2api throughput. A separate one-million-unit sustained pressure scene correctly rejected when outstanding maximum liability exhausted that explicit cap. A later clean automatic-default run using the real built-in estimator completed 27,564/27,564 requests over 60 seconds at 459.09 RPS versus paired sub2api 400.22 RPS, with exact financial drains. Its finite repeats retained one slow outlier; stability follow-up and the complete operational fault matrix remain separate gates, not inferred from the sustained pass.

The subsequent clean generation-6 test of local source `770d736` (published equivalent `6d755f6`) did not pass acceptance. Its first c32 pair completed 1,000/1,000 at 379.32 RPS versus sub2api 411.09 RPS (92.27%). The second fast scene returned 980 successes, 19 `FAST_CREDIT_NOT_READY` 429s and one `FAST_CREDIT_BUSY` 503; the zero-rejection gate stopped the run before the second sub2api scene and third pair. All 1,980 successful responses reconciled exactly, with no unknown settlement. The incomplete repeated run is a failure, not evidence of stable performance parity; the earlier sustained success does not override it.

The next clean generation-7 test of local source `6917e32` (published equivalent `e201439`) also failed overall acceptance. Three c32 pairs completed 3,000/3,000 successfully, with fast/sub2api throughput ratios 102.17%, 81.31%, and 91.11%; the second pair remains a failed stability sample. The 60-second sustained fast scene attempted 28,998 requests: 28,986 succeeded, nine returned `FAST_CREDIT_BUSY` 503 and three returned `FAST_CREDIT_NOT_READY` 429. Successful throughput was 482.75 RPS versus sub2api 366.77 RPS; this does not override the zero-rejection failure. There were 29,265 intent statements (267 beyond request count), all 28,986 successful upstream sends/receipts/ledger effects reconciled to charge 1,014,510, and no unknown liability remained. No cap, M, or estimator override was introduced.

Measurement correction: historic `completed_at - receipt.created_at` is **receipt-to-settlement-transaction-start**, because PostgreSQL `now()` is the transaction start timestamp. It is not durable settlement latency. Future diagnostics correlate successful receipt acknowledgements with the corresponding worker COMMIT acknowledgement; instrumented diagnostics are reported separately from clean timing runs. Historical raw artifacts are retained with this qualification, not relabelled as durable commit evidence.

## Read-side integration boundary

Fast usage is durable in intents/receipts/jobs, not fabricated legacy request/attempt/usage rows. The customer console now reads both stores through a tenant/project-authorized projection for request history/detail, usage totals and daily buckets; see [the read-side contract](fast-console-usage-read.md). Fast detail does not fabricate a legacy attempt timeline. Admin analytics, exports, webhooks, financial reports and direct legacy-table consumers remain outside that adapter; large-history indexing/query-plan acceptance is separate. Native acceptance counts both formats and reconciles their exact ledger effects.

## Pinned connection reuse

Connection reuse defaults on **only inside explicitly enabled fast mode**. `MODEL_ROUTER_FAST_CONNECTION_REUSE=0` (or `fastGateway.reuseConnections: false`) is the isolated rollback/A/B control; malformed values fail startup. Global fast mode remains off by default. Each request still validates its HTTPS URL, fresh DNS answer and approved pinned address. One borrower exclusively owns each dispatcher until upstream body EOF; cancellation, fetch failure and invalid/redirect responses destroy it. Completed direct-HTTPS dispatchers can be reused only for the same hostname/SNI, port, pinned address and address family. Each pool owns one immutable base TLS/CA/ALPN factory; proxy and TLS-fingerprint paths are excluded. Idle entries expire after 30 seconds; live entries are bounded (default256, tied to an explicit HTTP cap when set), with a bounded retirement queue and LRU eviction. Pool shutdown drains/closes its dispatchers. Whole-window measurements must include all refresh/worker activity; dispatcher reuse is the intended optimization, not omitted SQL attribution.

The hard-maximum text slice also checks an explicit safe field set on both the client request and the **compiled upstream body**. Unknown vendor extensions (`best_of`, `extra_body`, injected tools/search/media, etc.) fall back before Redis or money. This does not prove arbitrary vendors obey an OpenAI-shaped token limit: supported providers must honor the configured token-bound/commercial contract. The journal pins principal identity, authorization revisions and commercial-attestation identity once, rather than relying on mutable key/profile joins for historical attribution.

## Credit capacity is not an estimator benchmark shortcut

For a uniform hard maximum `M`, available concurrent liability is at most `floor(available_prepaid_credit / M)`, independently of Redis slot count. Unresolved intents reduce that available credit. Stripes partition the same configured tranche; they never multiply the spending cap. The built-in estimator reserves its configured input ceiling (commonly262144), whereas the original R9 fixture injected4096. In the measured built-in scene `M=524480`: an explicit1000000tranche funds exactly1 simultaneous full reservation;32 require at least16783360 available credit before unresolved liabilities. Matching the c32 performance fixture therefore requires an adequately funded automatic budget or explicit tranche; small-cap rejection is correct financial behavior. Never shrink `M` heuristically or silently raise a configured credit cap to improve timing. Report real-estimator and fixture-estimator scenes separately.

When the tranche setting is **unset**, native mode passes a server-derived concurrency bound (minimum tenant/project/key/account/local cap, at most1024) to the journal. Its automatic target is `2 × M × concurrency`, providing liquidity for asynchronous billing lag, always limited by real free wallet funds. It does not reduce M, authorize overdraft or multiply money by stripe count. Any explicitly supplied cap disables automatic expansion. `MODEL_ROUTER_FAST_CREDIT_STRIPES=1` is the comparison/rollback control; the normal stripe count is8. Auto liquidity is not a guarantee against arbitrary worker outage or an underfunded wallet; outstanding/unknown liability remains backed. Reserved per-owner liquidity is not spent money: a low-funded wallet can have usable fast credit on one owner while strict fallback or another owner sees less globally available credit. Explicit caps bound this fragmentation; graceful shutdown returns proven unused backing. Keep owner identities stable across restarts and unique across concurrent replicas. A drain-only worker must not fence a live admission owner or recycle unresolved maximum liability.

A client may omit its output limit only if the configured compiler injects a positive enforced bound. The final compiled payload is independently checked against the estimator before Redis or money reservation; a custom compiler that leaves the bound absent still uses strict mode.

Only an explicitly acknowledged no-intent/no-debit result permits bounded credit recovery; it never repeats Redis admission or upstream execution. Normal success stays one intent SQL. Recovery wait/new-attempt admission is limited to 100 ms and the original snapshot deadline/client cancellation; an in-flight database write remains uncertain on error, never retryable. Count recovery SQL and complete HTTP p99 including waits, not only final successes. See [the journal recovery contract](fast-billing-journal.md#acknowledged-no-write-credit-recovery).

Credit errors distinguish insufficient/not-ready capacity (`429 FAST_CREDIT_NOT_READY`) from a concurrent reservation race (`503 FAST_CREDIT_BUSY`); an expired send deadline and a closed journal are separate 503 codes. These newer profiles must not be merged with older runs that exposed one generic credit error.

## Readiness

When fast mode is enabled, health readiness also checks the existing Redis generation/run identity, configured recovery horizon and server-clock quarantine, journal owner startup, and the snapshot cache availability latch. The health-only check never creates/reset slots or restores a closed snapshot cache, and adds no request-path query. Redis PING alone is insufficient. Readiness is not a promise every tenant has prepaid capacity or that every request is in the fast supported subset.

## Rolling token quota semantics

Fast TPM admission reserves the conservative input+output token bound for in-flight work. After a validated **successful durable usage receipt**, the existing Redis release call reconciles unused tokens in that lease's original second bucket to actual input+output totals. RPM is never refunded. Financial maximum cost and prepaid backing are unchanged. Unknown execution, missing usage or failed receipt acknowledgement retain the full token reservation until its rate window expires. A pruned original bucket cannot debit a newer bucket.

All adjusted rate values and the released lease tombstone are committed in one same-slot atomic Redis `MSET`, so Lua runtime errors or lost acknowledgements cannot apply a token refund twice. The Redis ACL must permit `MSET` and `PEXPIREAT` as well as existing admission commands. A failure restoring TTL after MSET can retain state longer, but the tombstone prevents another refund; this is a cleanup/availability fault, not permission to reset quota state. No additional request roundtrip or PostgreSQL query is introduced.
