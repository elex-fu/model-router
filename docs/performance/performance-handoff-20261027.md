# model router 性能优化与验证收尾报告

截至 2026 年 10 月 27 日 22 时 36 分 北京时间

本报告汇总当前优化成果、固定资源性能实测、已验证的正确性、未解决问题及暂停后的恢复入口。当前不建议宣布已对齐 Sub2api，也不建议把双进程作为无条件性能优化。

## 核心结论

最新已完成的固定配额对照为 f2d9889：16 组全部通过诊断验证，242,120 次计时请求错误为零。总计 2 CPU、2 GiB 下，双进程每请求 CPU 比单进程高约 52%–56%，生命周期峰值内存高约 88%–107%，吞吐没有稳定全面提升。

关键发现是计费队列大量回退同步持久化。计时请求中 85,002 次回退，占 35.11%；200 并发各组回退率约 85%–88%。因此这轮不是“全部请求先响应、后内存队列计费”的性能。

当前远程提交 8d6482e7 的 78 项 CI 全部通过。它对应的第二轮固定配额任务仍在运行，未纳入本报告性能表。按暂停要求，不安排新开发、压测或自动重试。外部已运行任务未被取消，可能继续产生结果。

## 测试口径与最新执行流程

### 固定配额对照设计

每种负载按单进程、双进程、双进程、单进程的 ABBA 顺序执行。并发 32 与 200，JSON 与 SSE 共 16 组；每个配置仅有两次重复。所有应用容器使用同一不可变镜像，配额固定为 2 CPU 与 2 GiB，Docker MemorySwap 上限同为 2 GiB，表示内存与交换合计上限，而非额外 2 GiB 交换空间。

PostgreSQL、Redis、TLS 模拟上游与压测驱动在应用配额之外；它们仍共享宿主资源。模拟上游延迟约 5 毫秒，不代表真实大模型生成时延。32 并发每组持续约 60 秒；200 并发每组严格 10,000 个请求。每组另有 138 个预热请求。

| 约束 | 单进程 | 双进程合计 |
| --- | --- | --- |
| 数据库连接预算 | 16 | 16 |
| HTTP 在途上限 | c32 为 64；c200 为 256 | 相同，拆分到两个 worker |
| 计费队列总条数和字节 | 256 条／2 MiB | 相同，按 worker 分割 |
| 单租户队列容量 | 64 | 每 worker 32 |
| 回执并发与对账并发 | 各 8 | 每 worker 各 4 |
| 预留资金上限 | c32 67,133,440；c200 268,533,760 | 相同，总预算不扩张 |

### 请求处理与两条计费路径

请求进入后执行鉴权、路由、准入和资金约束，向模拟上游发起请求并处理 usage。计价、规范化与摘要尽量一次准备，内部可信回执复用；对外输入校验和落库身份校验保留。

队列接收：内存队列承担回执落库与后续 TPM 对账；请求侧可避开等待回执持久化。回执条目在 PG 确认后压缩，但队列容量和租户占用仍保留到对账完成。

队列拒绝：仍在 fast 模式内同步等待 journal.appendReceipt，随后完成实际用量释放，再结束请求。它不是回退旧计费模式，也不意味着多写一次回执。

双进程额外经过主进程 HTTP 转发、Unix socket 与内部许可消息；主进程没有 PG 连接池。固定总连接数下，单进程业务／配额池为 14／2，双进程合计为 12／4，分配并非完全相同。

### 当前最强线索

高并发下回执队列等待达到秒级，回执处理并发槽接近满占用。双进程每个 worker 的租户容量仅 32，条目从等待回执到完成 TPM 对账都占用容量。请求分发主要依据 HTTP 在途量，而不是计费队列占用，因此局部满队列与另一 worker 空闲可以同时存在。

真实 Redis lease 具备队列所需能力；本轮回执和对账重试均为零，冲突为零，最终全部排空。观察到的最大持久化延迟与驻留时间均低于 5 秒。拒绝原因尚无分类计数，因此“租户容量或字节容量导致拒绝”是强线索，不是已经证明的唯一根因。

### 不能据此推出的结论

同步回退明确把 PG 确认放回响应关键路径，但通常复用同一已准备回执，不天然增加一次回执写入。CPU 增加可能造成队列积压，也可能与回退共享其他原因，不能把全部额外 CPU 都归因于同步回退。

简单扩大队列可能只增加未持久化证据、资金占用及长尾，不等于提高处理能力。暂停后优先补足拒绝原因，再在不变连接池、资金与队列预算下比较后台并发及调度。

## 已完成改动与正确性验证

### 已经落实的优化方向

准备回执一次生成并内部复用，减少重复计价、规范化与摘要；保留外部校验、落库身份及独立结算复核。复用静态鉴权解析，保留实时到期、撤权、版本及实际发送前检查。队列调度与条目压缩减少重复扫描及大对象保留，但不删除可重试、可排空的 TPM 对账。

有界双进程引入请求级分配、私有控制通道、固定连接与资金预算、停旧启新的恢复流程和代际隔离；它目前是可验证的架构选项，而不是已证明更快的默认方案。

### 与先前优化评估相比的变化

准备回执单项版本曾出现吞吐下降，后续发现并移除新增的重复价格拷贝。前三项合并优化的 40,000 请求 ABBA 结果仍是混合：吞吐变化约 +3.03%／−0.21%，CPU 约 −3.87%／+0.94%，没有稳定提升。

串行筛查出现 JSON p99 改善而 SSE 回退，未形成总体收益。过去微观 CPU profile 存在负 timeDelta，原严格诊断失败；衍生热点仅作为候选方向，不作为性能通过证据。

本轮新增的价值是证据更完整：固定资源后双进程额外 CPU 成本稳定出现，并且首次明确统计大量请求转为同步回执写入。重点应从“异步开关已开启”转向“真正被队列接收的比例及后台完成能力”。
