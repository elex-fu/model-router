# Fast gateway durable money journal (migration 143)

This is an opt-in bounded-text vertical slice, not a replacement for every strict billing policy. The gateway must reject unsupported scopes **before** creating an intent. Client-supplied idempotency keys, finite key/group monetary budgets without a compatible durable allocation policy, media, non-neutral price overrides unbounded upstream output, and platform prices whose hard maximum rounds to zero stay strict (BYOK remains distinct and fast). Never fall back or retry upstream after an intent write has an uncertain result.

## Money and execution authority

* One autocommit SQL statement takes a shared process-epoch fence, atomically subtracts a verified hard maximum `M` from a gateway credit allocation and inserts an immutable intent. A duplicate insert rolls the entire statement back. A lookup after a duplicate can return only `existing`, never permission to send again.
* Off-path refill acquires the existing wallet advisory fence. It subtracts legacy reservations, refund freezes and **all** fast allocation backing before allocating. The explicit tranche setting caps each owner's active backing; it is not an overdraft allowance. Legacy wallet summaries, reserves, refunds and new negative corrections include fast backing.
* A generation takeover fences old owners. Retirement returns only unused available credit. Unresolved intent maxima never expire or become reusable because of a Redis restart, process exit or TTL.
* Before terminal HTTP success/EOF, one SQL statement appends an immutable usage receipt and its durable work row. An ambiguous append may be retried with the exact same receipt; a conflicting digest is rejected. Failed/unknown receipts retain money for reconciliation, except the explicitly trusted definitely-unsent tuple (`failed`, HTTP status null, charge `'0'`, empty usage object). That marker may be emitted only before entering transport; the worker releases its maximum exactly once. A completed non-2xx response or any ambiguous send can never use the marker.
* The worker claims durable jobs with `FOR UPDATE SKIP LOCKED`, recomputes exact bigint charges `C` from the frozen price, verifies usage bounds and `C <= M`, posts balanced immutable ledger entries, adjusts the wallet and credit allocation, and completes the job in one transaction. A crash rolls everything back. Active allocations regain `M-C`; retired allocations release their entire `M` backing while charging `C` once.
* Native PostgreSQL command tags are checked: a resolved `ROLLBACK` response to `COMMIT` is not reported as a committed transaction. Lost ACKs are still uncertain, never permission to replay upstream.

## Runtime contract

`createFastGatewayJournal(database, {allocationOwner, allocationTrancheMinorUnits?, allocationStripes?, workerPollMs?, workerBatchSize?, onBackgroundError?, onCreditUnavailable?, onCreditRecovery?})` starts the durable worker. Use the existing gateway role. `replenish(tenantId, currency, minimumReserveMinorUnits?)` prewarms credit (pass the supported hard maximum to avoid cold fragmentation); an empty-credit denial schedules the same work automatically off the request path. `drain()` settles available successful receipts; `close()` stops admissions/polling, drains and retires unused credit. Neither removes unknown liabilities. `calculateFastReceiptCharge` is shared with the gateway's pre-EOF validator.

Migration 145 defaults to up to eight independently locked allocation stripes per owner/wallet, sharing **one total tranche cap**. A bounded (1024-wallet) local round-robin hint spreads admissions; eviction cannot allocate money. Candidate discovery is unlocked, then exactly one row receives a guarded CAS: no rotated multi-row lock scan or deadlock-prone retained locks. Concurrent depletion can conservatively return `credit_busy` (distinct from `credit_not_ready`, observable via `onCreditUnavailable`), never financial insufficient-funds proof and never permission to resend. The normal success remains one foreground intent SQL; only an explicitly acknowledged no-write result permits the bounded recovery described below.

Off-path refill locks allocations in sorted order under the wallet fence, redistributing only unused available credit and preserving each stripe's unresolved backing. Known hard maxima select fewer stripes when four-M headroom per stripe is unaffordable; near-tranche requests use one stripe. A funded first admission now awaits bounded singleflight cold credit preparation with its known M before writing an intent; an inadequate prewarm hint similarly awaits rebalance. Warm admissions add no readiness SQL. The deadline is rechecked after this cold work, and cold transaction/wait latency must remain in HTTP measurements. Hint eviction can repeat cold work, never grant money. Conservative busy denials are real HTTP failures and must be counted in benchmarks, not hidden. The worker claims up to 128 receipts per transaction, posts per-intent immutable ledger pairs in one statement and aggregates wallet/credit projections. Wallet fences are acquired in deterministic order across mixed-wallet batches. Empty polling backs off to one second; local receipt notifications only shorten that durable polling interval. A 40-receipt same-wallet test observes 10 SQL operations inside one transaction (12 including BEGIN/COMMIT), separate from the two foreground writes. Receipt and intent tables are durable money records; existing audit/usage UI tables are not yet projected by this module. Migration 144 adds the audited operator recovery path below; there is still no TTL release.

## Acknowledged no-write credit recovery

A statement returning exactly `{id: null, credit_busy: boolean, credit_recoverable: boolean}` has created **no intent and no debit**. Only that result can enter recovery: one fresh-snapshot selection after a concurrent candidate depletion, and at most one recovery after not-ready credit. Both reuse the same frozen intent ID, request/attempt identity, money, snapshots and original send deadline. Exceptions, lost commit acknowledgments, malformed results and unique conflicts never enter this loop. A replay lookup remains `existing`, never new sending authority. Redis admission/RPM is not repeated and upstream is never retried.

The failure-only aggregate examines this owner's at most eight active stripes. A total unused balance at least `M` with no individual stripe admitting `M` proves fragmentation and permits joining a singleflight wallet-fenced rebalance. PostgreSQL `EXPLAIN ANALYZE` verifies that this aggregate is **never executed on successful warm admission**; it does not scan global pending jobs. Without that fragmentation hint, an already-running local worker may be awaited as a scheduling hint, not a promise of money. Every next intent still uses the durable guarded CAS. Real insufficient credit with no running worker returns immediately after the original failed CAS and replay check; the existing rate-limited background refill remains unchanged.

The fixed **100 ms wait/new-attempt budget** begins at the first acknowledged no-write result (four normal 25 ms polling periods). It is not a financial TTL or a configurable capacity increase: it only bounds transient recovery waiting and whether another CAS may start. The original snapshot deadline or client abort wins earlier. Already-in-flight SQL is not canceled or represented as having rolled back; its latency can exceed this budget and its uncertain outcome remains fail-closed. A timed-out refill remains tracked for drain, but completing it later never starts an intent. No unresolved/unknown maximum is released by elapsed time, cancellation or recovery.

Wait completion carries an explicit outcome (`completed`, `cancelled`, `authority_expired`, or `budget_exhausted`). A timer wake is not proof that a deadline elapsed: early wakes recheck wall/monotonic clocks and re-arm with a rounded-up delay of at least 1 ms. Work completion also rechecks both limits; observed authority expiry/cancellation is never reclassified as credit shortage by a later clock read.

Report recovery counts (`onCreditRecovery`, or intent statement count minus original attempts), extra replay/refill SQL, and full HTTP p99 including waits. At most three intent statements can occur for an unusual request encountering both failure kinds; normal success remains one. Final `credit_not_ready` and `credit_busy` retain their original HTTP meanings and must be counted as failures. The real PostgreSQL gate covers fixed-cap eight-stripe fragmentation, actual blocked EPQ depletion, recovered-write ACK loss, cancellation/deadline/budget expiry, warm aggregate non-execution, and genuine insufficiency without a recovery queue.

## Audited unknown recovery (migration 144)

The control-plane-only `/admin/api/v1/ops/fast-unknown-outcomes` endpoint lists cases (`GET ?tenantId=...`), reads a case (`GET /:intentId?tenantId=...`) and accepts an append-only resolution (`POST /:intentId/resolve?tenantId=...`). It requires an active operations/superadmin session; POST additionally requires same-origin, CSRF and an `Idempotency-Key`. The exact JSON fields are `kind`, `chargeMinorUnits`, `usage`, `evidenceReference`, `evidenceSha256`, `supportTicketRef`, and `reason`. Actor identity comes only from the authenticated session.

`verified_usage` recomputes exact usage against the frozen price and maximum. `non_execution` requires positive trusted operator attestation of provider non-execution, charge `'0'` and empty usage. The evidence reference/hash is an audited human attestation, **not automatically verified provider proof**. Passing the last-send deadline is only an eligibility guard, never evidence that execution finished or did not happen. No timeout, missing receipt or support ticket alone authorizes release. Operators must not resolve a still-running or unverified call.

A resolution does not modify the original intent/receipt. It queues the same durable worker (202 means pending, not financially complete), which atomically settles once. Missing receipts can be resolved without fabrication; genuine late receipts remain immutable evidence and do not override an already-authoritative resolution. Conflicting evidence requires separate incident review, not a second resolution/debit. Authorization is rechecked behind the revocation fence and again after waiting for a job lock. Gateway credentials cannot create operator resolutions.

**145 rollout:** drain/disable fast mode before applying 145 and replacing gateway processes. The active allocation unique key changes to include `stripe`; pre-145 refill SQL is not rolling-compatible and fails closed after migration. Strict rollback remains available, but do not run an old fast gateway binary against the new schema. Never rewrite a published migration checksum.


## Default auto credit policy (explicit caps are unchanged)

When `allocationTrancheMinorUnits` is **omitted**, the budget target for each owner/wallet is the high-water maximum of `2 × hard maximum M × trusted supported concurrency` observed in that process, using exact BigInt arithmetic (saturated at the PostgreSQL wallet range). Concurrency must be an integer 1–1024 supplied by the gateway from the minimum applicable snapshot and local concurrency caps, never a request body/header. The factor 2 is an explicit receipt-lag headroom policy, not a lower price estimate or an overdraft. It cannot promise unlimited progress under an indefinitely delayed worker or unresolved calls. Passing an explicit tranche keeps that hard cap exactly; it is never auto-multiplied.

Cold preparation/target expansion happens before any intent. Refills still hold the existing wallet fence and fund only `min(target − current own backing, genuinely free wallet funds)`, after subtracting strict holds, refund freezes and all owners' fast backing. Stripes share that total. No ambiguous-write retry, hidden negative wallet balance or unknown-money timeout is introduced.

**Liquidity tradeoff:** an automatic owner may escrow most free wallet funds and temporarily limit other gateways, strict spending and refunds. A high-water target can retain unused escrow for the process lifetime. Operators can drain/close the gateway (or explicitly retire its allocations) to return only unused credit; unresolved maxima remain backed and require the audited resolution path. There is no automatic idle/TTL release of unresolved money. Retiring unused escrow is not a ledger spend/refund and does not change posted wallet balance.


Background credit refill attempts are singleflight and rate-limited per wallet by a monotonic 250ms cooldown; unchanged allocation projections do not issue an UPDATE. First cold preparation and a known larger M/automatic target bypass that cooldown and remain deadline-bounded before the first intent. This is only a load-shedding hint: it cannot free unresolved money, allocate funds or change a denied intent into sending authority. Newly available funds may take up to the cooldown to trigger background refresh. With a small explicit cap, even a funded wallet can briefly reject a request after settlement until that refresh restores credit; count those statuses and queue/cooldown latency, not just successful-request latency.

## Fast-off recovery worker

Disabling fast admission must not strand already durable billing work. Run the **explicit opt-in** `model-router saas:fast-billing-worker` command with `MODEL_ROUTER_SAAS_GATEWAY_DATABASE_URL` authenticating as the existing non-owning gateway login. It verifies schema/runtime privileges and uses verified TLS by default; `--allow-local-plaintext` is only for explicitly configured loopback/disposable PostgreSQL. It never runs migrations/grants and loads no Redis, snapshots, KMS, HTTP admission or upstream transport. A fresh, unconfigurable `billing-drain:<uuid>` owner namespace cannot take over a live gateway owner.

The default daemon polls durable jobs, remains alive with an idle pool, and drains/closes on SIGTERM/SIGINT. `--once` processes immediately claimable jobs and exits; `SKIP LOCKED` means another worker can still own pending jobs, not that the global queue is empty. `processedJobs` includes jobs conservatively blocked by validation; it is not a count of successfully charged requests. Failed/unknown/missing-receipt liabilities remain backed and require audited resolution. A later operator resolution is settled by this same worker even with the native fast gateway disabled. No worker is silently added to ordinary strict-mode startup.

Use `--batch-size 128` and `--poll-ms 250` (defaults) or bounded explicit overrides. The standalone daemon aborts, closes and exits nonzero on a background processor/startup failure (even if diagnostic output fails), so a supervisor can restart it. Fatal cleanup uses explicit `close({drain:false})`: it waits for already-started work only, never claims another job or retires credit. This is stop-not-drain; pending jobs and all unused/unresolved backing remain durable for restart. Normal close/drain and the HTTP journal retry policy are unchanged. Monitor safe error events and restart on connection/role failures; SIGKILL leaves atomic claims/ledger effects replayable. Drain/close admission before shutting down the final worker when possible; continuing producers can extend graceful drain time.

Admission gateways must keep `MODEL_ROUTER_FAST_OWNER` stable across restarts and unique among live replicas. A normal same-owner restart fences the old epoch; subsequent credit preparation retires only that old epoch's unused credit. Changing the owner after SIGKILL can strand unused old-owner escrow until an explicit, fenced operational retirement. The drain-only command deliberately does not impersonate a gateway owner or reclaim another owner's allocations. Neither owner changes nor daemon restarts permit recycling unresolved maxima by TTL.

## Settlement credit-lock scope

The worker reads immutable allocation identity/state under the existing sorted wallet fences, without locking admission credit rows during ledger construction. Refill, retirement and settlement all share those fences; native admission can only subtract available credit. After inserting the complete ledger batch, the worker explicitly runs the two existing named deferred balance constraints with `SET CONSTRAINTS ... IMMEDIATE`, before wallet projection and credit locks. This adds one SQL operation per paid batch; it moves the same mandatory checks out of the credit-lock window, never disables or replaces them.

A late, separate SELECT acquires sorted `FOR NO KEY UPDATE` locks and checks the original tenant/wallet/currency/epoch/state tuple again. The next guarded statement restores credit additively from current row values, including any native CAS that committed while lock acquisition waited. Keeping these commands separate avoids same-statement snapshot/EPQ ambiguity. Together with the balance-check flush, this adds two SQL operations per paid batch versus the original early-lock worker. Any tuple mismatch, missing row or balance-check failure rolls back the entire ledger/projection/job transaction. Only credit restoration, job completion and COMMIT retain these scarce row locks. The existing strict wallet fence still covers the complete financial transaction. This is a lock-scope change, not a measured HTTP performance claim.
