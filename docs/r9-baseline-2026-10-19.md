## 诊断发现（本次重跑的核心增量）

1. **池不是瓶颈**（修正既往假设方向）：
   - 空闲时 PG 仅 3 idle 连接；压测峰值未见连接堆积证据。
   - `bench-pool32` 诊断 overlay（池 16→32）后 3 实例：吞吐反而降到 **1.88 rps**、p50 延迟升到 **31.8s**——池扩容未缓解，排除纯池瓶颈。
2. **单请求处理时间 ~170-450ms**（mock 直连 3ms）：空闲态单请求 0.65s 端到端。这是 latency/ttfb overhead 的直接构成——**每请求的网关处理成本**（prepare/admission/dispatch/settlement 链的 SQL 往返串），而非排队。
3. **高并发 503 主导**：c=200 时 65% 请求 503。日志无 crash；`sql_error: timeout exceeded when trying to connect` 出现于压测峰值（pool16 时）——admission 链的 SQL 在并发下争用。
4. **结论**：瓶颈形态指向 **prepare/admission 链的每请求多轮 SQL 串行往返 + 容量准入在并发下的争用**——正是主方案 §10.1/10.2 第一级优化（"批量读取不可变价格/版本和 guard 数据，合并独立 SQL 往返"）的靶点。B08 缺口在新 main 上**确认仍存在且已定位到具体阶段**。
