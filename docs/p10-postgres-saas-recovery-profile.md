# P10 owned PostgreSQL immediate-stop recovery

This optional diagnostic profile reuses the disposable R9 stack and starts one additional standard control-plane CLI, whose unchanged production recovery scanner runs automatically. It is separate from Redis old-snapshot recovery and from every performance mode. It proves neither HA, PITR, storage power-loss durability, real-provider behavior, builtin acceptance nor full R9 acceptance.

Historical checks passed the three syntax checks, six PostgreSQL profile pure units plus the five original Redis units (11/11), and a server build at `7e4fd2852876671672688e7fcdf5a91704f8c640`. Run-05 later used the fresh build and provenance described below. The complete recovery profile has not passed. Pure assertion/flag tests cannot replace it. Execution requires the dedicated local slot and a separately frozen current server build and dependencies. PostgreSQL 16+ tools, Redis, OpenSSL and Node must be installed. The supervisor creates its own fresh database, normal migrations and three restricted roles, local Redis and HTTPS mock; external role URLs are not required. Control-plane listener readiness follows the standard compose contract: both owned customer/platform loopback ports must accept TCP connections while the child has no exit code or signal. No platform `/readyz` route is assumed; the later scanner result remains the recovery capability proof.

Use a new private output directory. No benchmark runs. Tracing, ingress caps, request samples, serial, cap and Redis recovery modes are excluded. Source/dist/harness provenance and normal owned cleanup remain recorded. The temporary local TOTP provider key is passed only to the control-plane child environment, not to gateways or command arguments. This local fixture KMS is not production-KMS evidence.

The mock sends a genuinely slow SSE response. After the first real bytes, the profile observes the original durable `dispatching` attempt, positive platform hold and live provider lease. It records fixed-field PG authority and database identity. The observation pool closes, then a supervisor closure runs `pg_ctl -D <its fixed owned pgdata> -m immediate stop`; no external path, reinitialization, SQL financial mutation, clock manipulation or TTL override is accepted. Gateways, Redis, mock and control-plane processes must remain alive. The original stream must fail naturally through the existing heartbeat/transport timeout before the client deadline, and mock `currentInFlight` must reach zero while PG is still stopped. Three new unique requests across the three gateways must fail closed without increasing mock dispatch count or creating an active upstream response.

The same owned data directory and port restart. Role/database/address/port/version, `fsync=on` and `synchronous_commit=on` must match, and `pg_postmaster_start_time()` must change. Original wallets, ledger entries, usage, settlements, hold identity/amount and cumulative key budgets must remain unchanged. The original request must still be pending before scanner eligibility; an early unknown or other divergent state is a failure, not patched into the desired state.

Recovery then waits naturally for the existing **600,000 ms stale horizon plus the 5-second scanner cadence**. The overall observation deadline is 15 minutes from profile start; it does not reduce the production horizon, lease TTL, heartbeat or 60-second transport timeout. Progress is written and printed approximately every 30 seconds to support operator updates. The standard control-plane scanner must produce exactly one `operator_required` case with no error, and the original request must become `unknown / reconciliation_pending / pending`. Original budget reservation identity, lineage, day, token units and charge must remain exactly equal to the pre-stop facts after scanning and the fresh request; both daily/lifetime outstanding counters must equal those original amounts. Original lease identity and fence must remain unchanged, with **zero live held leases**; a physically stored `held` row whose DB-clock expiry passed is valid and is not misreported as released.

Canonical replay from another gateway must return 202 and the original canonical ID, with no additional dispatch, usage, ledger, budget or lease effect. One fresh short request must then settle exactly once, with the same strict token/charge budget increments, wallet debit and one balanced linked billing transaction/two entries as the Redis profile. The original unknown request/hold remains unresolved. A legitimate fresh acquisition may lazily classify an expired lease; no synthetic acquisition is used to force its stored status.

All financial observations use read-only transactions and a five-second statement timeout. `postgres-saas-recovery.json` retains safe fixed-field authority snapshots, identity, crash/restart phases and scanner/lease facts. `postgres-saas-recovery-progress.json` reports current progress. Signal cancellation reaches HTTP reads, polling and supervisor actions; cleanup remains the supervisor's responsibility, including a possible server whose startup command was interrupted. Any actual process crash, unexpected request success, scanner failure or financial drift fails the profile and must be diagnosed before expanding the scenario matrix.
